# M2.3 — Physical frame allocator: measured evidence

- Date: 2026-10-21
- Host: Fedora Linux 44 (x86_64)
- Zig: 0.17.0
- QEMU: 10.2.2 (`qemu-system-x86_64`)
- Firmware: OVMF `edk2-ovmf-20260812`
- Machine: QEMU `q35`, 512 MiB, one CPU, OVMF with a copied NVRAM store
- Branch: `feat/m2.3-physical-frames` (pending pull request and CI)
- Specification: `docs/specs/m2.3-physical-frames.md`
- Decision: `docs/adr/ADR-0009-physical-frame-allocator.md`

All values below are serial output or command output, not a reconstruction.
Addresses belong to the build that produced each log; rebuilding changes
them, so the tests parse the log instead of hardcoding them.

## Commands executed

```sh
zig fmt --check build.zig boot kernel shared tools
zig build
zig test kernel/mm/frames.zig
zig build test
```

Result: **PASS** for every step.

`zig build test` runs the host unit tests, the boot test, the fault handler
test, the `ExitBootServices` retry test and the double fault test.

## Host unit tests

`zig test kernel/mm/frames.zig`:

```
1/8 frames.test.init marks every frame used...OK
2/8 frames.test.init rejects an empty bitmap and an undersized buffer...OK
3/8 frames.test.free, allocate and release reuse the same frame...OK
4/8 frames.test.release rejects unaligned, out of range and double frees...OK
5/8 frames.test.reserve aligns outwards and wins over a free range...OK
6/8 frames.test.free aligns inwards and does not release partial frames...OK
7/8 frames.test.ranges are clipped to the covered capacity...OK
8/8 frames.test.stress: exhaust, release and reuse without overlap...OK
All 8 tests passed.
```

The stress test uses 2,048 bytes of bitmap = 16,384 frames = 64 MiB. It
reserves a 1 MiB kernel-like range and an 8 KiB loader-like range, allocates
all 16,126 free frames while checking alignment, uniqueness and the absence
of reserved addresses, releases every third allocated frame, reallocates
exactly that many with a second duplicate check, and returns to the original
free count.

## Normal boot

Command:

```sh
zig build boot-test
```

Relevant serial output (CRLF removed):

```
[azura] === AzuraOS kernel v0.1.0 (M2.3) ===
[azura] kernel image: 0x100000..0x12d200
[azura] memory: conventional=464 MiB boot_services=42 MiB loader=156 KiB
[azura] memory map buffer: 0x1e6a9018 (loader_data)
[azura] frame allocator: 130904 frames, 118579 free, 12325 used (511 MiB covered)
[azura] frame allocator: bitmap=16363 bytes, boot_services=42 MiB quarantined, above 4 GiB=0 MiB ignored
[azura] frame allocator: reserved low 1 MiB, kernel image, boot stack, boot_info, map and framebuffer
[azura] frame allocator: self-test ok, allocated 0x12e000 0x12f000 0x130000 and reused 0x12e000
[azura] post-ExitBootServices: stack=ok gdt=ok idt=ok tss=ok ist=ok frames=ok framebuffer=ok memory_map=ok
[azura] boot complete, halting
```

What each value proves:

* `130904 frames ... 511 MiB covered` — the bitmap covers the highest
  conventional or boot services address below 4 GiB. It is 16,363 bytes, so
  only the used prefix of the 128 KiB static buffer is active.
* `118579 free` — 118,579 frames = 463.2 MiB of conventional memory remain
  after the low 1 MiB, the kernel image, the loader data, ACPI, reserved
  ranges and the other non-conventional descriptors are taken out.
* `12325 used` — the used set also includes the 42 MiB of boot services that
  are covered by the bitmap but quarantined.
* `boot_services=42 MiB quarantined` — the class was not freed. The active
  firmware page tables live there; see ADR-0009.
* `reserved low 1 MiB, kernel image, boot stack, boot_info, map and
  framebuffer` — the explicit reservations ran after the conventional
  ranges were freed.
* `allocated 0x12e000 0x12f000 0x130000 and reused 0x12e000` — the first
  free frame is above `kernel_end=0x12d200`; the three frames were written,
  released and reallocated lowest-first. The self-test checks the frames
  against the kernel image, stack, `boot_info`, map and framebuffer before
  writing.
* `frames=ok` — the allocator and the self-test completed before the summary.
* The boot test requires `frame allocator:` and
  `frame allocator: self-test ok` in order before the summary, and still
  checks the framebuffer checksum and the memory map key.

## Fault path after the allocator is active

Command:

```sh
zig build fault-test
```

The test injects `#UD` and `#GP` after the allocator and self-test have run.
Both logs contain the allocator lines, the summary with `frames=ok`, and a
handler stack inside the boot stack:

```
[azura] frame allocator: self-test ok, allocated 0x12e000 0x12f000 0x130000 and reused 0x12e000
```

```
[azura] frame allocator: self-test ok, allocated 0x12e000 0x12f000 0x130000 and reused 0x12e000

[azura] KERNEL FAULT: rip=0x102fcf cs=0x8 rflags=0x46
[azura] KERNEL FAULT: error_code=0x0
[azura] KERNEL FAULT: handler stack=0x12d127

```

The test output:

```
PASS: the processor switched to the IST stack on a double fault
      IST:     0x129190..0x12d190

```

The handler stack is inside the IST range and outside the boot stack, so the
allocator did not disturb the alternate stack. Exactly one bootloader banner
and one kernel banner appear, so the machine did not reset.

## Limitations of this evidence

* Everything was measured in QEMU/OVMF; no physical hardware was exercised.
* The kernel still runs on the firmware's identity-mapped page tables. The
  self-test only writes to the first free frames, just above the kernel
  image; a future caller that allocates high memory before M2.4 could fault
  on an unmapped frame.
* Boot services are covered by the bitmap but remain used. The 42 MiB are
  not available to the allocator until M2.4 installs the kernel's own page
  tables and releases the quarantine.
* The bitmap describes the first 4 GiB only. Memory above it is reported and
  ignored. The QEMU machine has none in that range.
* The allocator has no concurrency control; the kernel runs with interrupts
  disabled and one CPU context.
* The self-test exercises three frames at boot; the exhaustive allocation
  and release coverage is the host stress test, not the QEMU run.
* The bitmap is a 128 KiB static buffer in `.bss`, which grows the kernel
  image even on a machine with much less RAM.
