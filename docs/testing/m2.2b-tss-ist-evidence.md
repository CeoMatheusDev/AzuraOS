# M2.2b — TSS and IST: measured evidence

- Date: 2026-10-21
- Host: Fedora Linux 44 (x86_64)
- Zig: 0.17.0
- QEMU: 10.2.2 (`qemu-system-x86_64`)
- Firmware: OVMF `edk2-ovmf-20260812`
- Machine: QEMU `q35`, 512 MiB, one CPU, OVMF with a copied NVRAM store
- Branch: `feat/m2.2b-tss-ist`
- Specification: `docs/specs/m2.2b-tss-ist.md`
- Decision: `docs/adr/ADR-0008-tss-and-ist.md`

All values below are output of the serial driver, not a reconstruction. The
addresses are link-time addresses of the image that produced each log; the
normal boot and the double-fault build place the kernel objects at slightly
different addresses because the test build adds the injection code.

## Commands executed

```sh
zig fmt --check build.zig boot kernel shared tools
zig build
zig build test
```

`zig build test` runs the host unit tests, the boot test, the fault handler
test, the `ExitBootServices` retry test and the double fault test.

Result: **PASS** for every step.

## Host unit tests

`zig build unit-test` passes, including the new tests:

* `kernel/arch/x86_64/tss.zig`: architectural size 104 bytes, field offsets
  (`rsp0` at byte 4, `ist1` at byte 36, `iomap_base` at byte 102), descriptor
  round trip with a base above 4 GiB, access byte `0x89`, `init` values,
  disabled I/O bitmap and the IST stack probe.
* `kernel/arch/x86_64/ist.zig`: only vectors 2, 8 and 18 use IST 1; ordinary
  vectors keep IST 0.

```sh
zig build boot-test
```

Relevant serial output (CRLF removed):

```
[azura] === AzuraOS kernel v0.1.0 (M2.2b) ===
[azura] kernel image: 0x100000..0x10b7c0
[azura] stack: base=0x1e00c018 top=0x1e010018
[azura] framebuffer checksum: 0xd43a1e5ec0808a0d
[azura] IDT installed, provisional selector 0x38
[azura] TSS: selector=0x18 base=0x1066a0 limit=103
[azura] TSS: rsp0=0x1e010018 ist1=0x10b790 iomap_base=104
[azura] IST1 stack: base=0x107790 top=0x10b790
[azura] IST1 stack: writable at 0x10b788
[azura] TSS loaded, task register=0x18
[azura] TSS descriptor: base=0x1066a0 limit=103 access=0x8b flags=0x0
[azura] IDT: IST 1 active for vectors 2, 8 and 18
[azura] IDT installed, exception handling active
[azura] IDT: base=0x106790 limit=4095
[azura] post-ExitBootServices: stack=ok gdt=ok idt=ok tss=ok ist=ok framebuffer=ok memory_map=ok
[azura] boot complete, halting
```

What each value proves:

* `TSS: ... base=0x1066a0 limit=103` — the TSS is inside the kernel image and
  its descriptor covers the 104 architectural bytes.
* `rsp0=0x1e010018` — equal to the boot stack top reported by the
  bootloader; the ring 3 -> ring 0 field is not zero.
* `ist1=0x10b790`, `IST1 stack: base=0x107790` — a 16 KiB range inside the
  kernel image, ending exactly at `ist1`.
* `IST1 stack: writable at 0x10b788` — the top word was written and read back
  before any fault needed it.
* `TSS loaded, task register=0x18` — `LTR 0x18` succeeded and `STR` reads the
  selector back.
* `access=0x8b` — the descriptor is present, DPL 0, type 11 (busy 64-bit
  TSS); `LTR` changed the encoded type 9 to type 11.
* `IDT: IST 1 active for vectors 2, 8 and 18` — every gate was checked
  against the policy after the final installation.
* The summary includes `tss=ok ist=ok` and still reports the M2.2 checks.

The boot test also asserts the framebuffer checksum the bootloader computed
(`0xd43a1e5ec0808a0d`) and the one the kernel recomputes are equal, and that
the memory map key received by the kernel is the one the successful
`ExitBootServices` call used.

## Forced double fault

Command:

```sh
zig build double-fault-test
```

The build injects `-Dfault-mode=double_fault`. At run time the kernel hides
vector 13 from the IDT (limit 143, vectors 0..8 visible) and executes
`int $13`. The #GP gate is outside the limit, so its delivery fails and the
processor raises #DF through vector 8, which is inside the limit and names
IST1.

Serial output:

```
[azura] TSS: selector=0x18 base=0x1066e0 limit=103
[azura] TSS: rsp0=0x1e010018 ist1=0x10b7d0 iomap_base=104
[azura] IST1 stack: base=0x1077d0 top=0x10b7d0
[azura] IST1 stack: writable at 0x10b7c8
[azura] TSS loaded, task register=0x18
[azura] TSS descriptor: base=0x1066e0 limit=103 access=0x8b flags=0x0
[azura] IDT: IST 1 active for vectors 2, 8 and 18
[azura] post-ExitBootServices: stack=ok gdt=ok idt=ok tss=ok ist=ok framebuffer=ok memory_map=ok
[azura] fault injection requested, hiding vector 13 to force a double fault
[azura] KERNEL FAULT: vector 8 (double fault)
[azura] KERNEL FAULT: rip=0x102697 cs=0x8 rflags=0x46
[azura] KERNEL FAULT: error_code=0x0
[azura] KERNEL FAULT: handler stack=0x10b767
[azura] KERNEL FAULT: machine halted
```

The test asserts:

* the expected markers appear in order, including the TSS setup, the IST
  verification, the post-transition summary and the fault report;
* the report has `cs=0x8` and `error_code=0x0` (the #DF error code);
* the handler stack `0x10b767` is inside the IST range
  `0x1077d0..0x10b7d0`;
* the handler stack is outside the interrupted stack
  `0x1e00c018..0x1e010018`;
* exactly one bootloader banner and one kernel banner appear, so the machine
  did not reset through a triple fault;
* there is no `FATAL`, `BOOT ABORTED` or "the injected fault did not fault".

Test output:

```
PASS: the processor switched to the IST stack on a double fault
      IST:     0x1077d0..0x10b7d0
      handler: 0x10b767
```

## Ordinary faults stay on the interrupted stack

Command:

```sh
zig build fault-test
```

This test still injects `#UD` (vector 6, no error code) and `#GP` (vector 13,
error code `0xa0`). Both reports now include the handler stack, and the test
asserts it lies inside the boot stack:

```
[azura] KERNEL FAULT: vector 6 (invalid opcode)
[azura] KERNEL FAULT: rip=0x10265e cs=0x8 rflags=0x10002
[azura] KERNEL FAULT: handler stack=0x1e00fd07
[azura] KERNEL FAULT: machine halted

[azura] KERNEL FAULT: vector 13 (general protection fault)
[azura] KERNEL FAULT: rip=0x102663 cs=0x8 rflags=0x10002
[azura] KERNEL FAULT: error_code=0xa0
[azura] KERNEL FAULT: handler stack=0x1e00fd07
[azura] KERNEL FAULT: machine halted
```

`0x1e00fd07` is inside `0x1e00c018..0x1e010018`, so ordinary faults did not
switch to the IST. The test output is `PASS: the kernel exception handler
reported both injected faults and halted the machine`.

## Limitations of this evidence

* Everything was measured in QEMU/OVMF; no physical hardware was exercised.
* The TSS setup is verified by reading the GDT, the task register and the TSS
  fields back; the CPU's own descriptor validation is exercised by `LTR`
  (a bad descriptor would have raised #GP before the checks).
* The double fault is injected by truncating the IDT limit; it is a real
  processor #DF, but it is not a spontaneous fault.
* The handler still halts the machine. Recovery, per-task kernel stacks and
  ring 3 are later milestones.
* The addresses above belong to these two builds. Rebuilding changes them;
  the tests parse them from the log instead of hardcoding them.
