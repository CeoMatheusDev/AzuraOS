What this proves:

* the key passed to `ExitBootServices` (0x731) is the key of the final map
  snapshot, and the kernel receives the same key;
* the call succeeded and no firmware console line appears after it (`jumping
  to the kernel entry point` is written directly to COM1);
* the stack probe at 0x1e010d60 is inside the reported range and the value
  read back matches the value written;
* the GDT and the IDT read back the addresses the kernel built (`0x105350`
  and `0x1053d0`, both in the kernel image);
* the framebuffer checksum after the handover equals the one the bootloader
  computed before it (0xd43a1e5ec0808a0d), so the MMIO mapping survived;
* the 85-entry memory map is readable after the transition and describes its
  own buffer as `loader_data`.

## 3. Retry path: a stale key is detected and recovered

The normal boot gets the key right on the first attempt, so the retry path
is exercised by building the bootloader with `-Dstale-map-key=true`. That
build allocates one page between the final snapshot and the call, which
changes the map and makes the key stale by construction.

Command:

```sh
zig build esp -Dstale-map-key=true -Desp-image=zig-out/test-ebs-retry/azura-esp.img
AZURA_QEMU_TIMEOUT=90 AZURA_QEMU_COMPLETION_MARKER="boot complete, halting" \
  bash tools/run-qemu-m1.sh zig-out/test-ebs-retry/azura-esp.img zig-out/test-ebs-retry
```

From `zig-out/test-ebs-retry/serial.log`:

```
[azura] final memory map: 85 entries, key=0x731
[azura] ExitBootServices: attempt 1, key=0x731, entries=85
[azura] ExitBootServices: injected a stale key
[azura] ExitBootServices: stale key, refreshing the memory map
[azura] final memory map: 85 entries, key=0x733
[azura] ExitBootServices: attempt 2, key=0x733, entries=85
[azura] ExitBootServices: success
[azura] boot services exited, map key=0x733
[azura] jumping to the kernel entry point
[azura] boot services: exited, memory map key=0x733
[azura] post-ExitBootServices: stack=ok gdt=ok idt=ok framebuffer=ok memory_map=ok
[azura] boot complete, halting
```

OVMF answered the stale key with `EFI_INVALID_PARAMETER`, the bootloader took
a new snapshot (key 0x733), and the kernel received the new key. The test
asserts that the two attempt keys differ; a bootloader that ignored the
failure and reused 0x731 would fail the test.

## 4. The exception path after the transition

Both fault injections run in a kernel that has already exited the boot
services. From `zig-out/test-fault-invalid_opcode/serial.log` and
`zig-out/test-fault-bad_segment/serial.log`:

```

[azura] KERNEL FAULT: vector 6 (invalid opcode)

[azura] KERNEL FAULT: machine halted

```

[azura] KERNEL FAULT: rip=0x101e74 cs=0x8 rflags=0x10002

Both frames are decoded correctly (`cs=0x8` is the kernel code selector), so
the IDT and the stack still work after the firmware is gone.

## Known limitations

* The tests run in QEMU/OVMF only. No physical machine has been tested.
* The kernel still runs on the firmware page tables (CR3 is logged on every
  boot). Installing its own is M2.4.
* The memory map is the pre-`ExitBootServices` snapshot. The `boot_services`
  total in the log is free memory in hardware terms, but the kernel does not
  allocate it until M2.3 (ADR-0007).
* The kernel image range is not re-typed in the firmware map; it is reserved
  by the boot protocol and must be subtracted by the M2.3 allocator.
* There is no TSS or IST stack yet. A fault while the kernel stack is
  corrupted still has no alternate stack; that is the next step after M2.2.
  *Addressed by M2.2b: see `docs/testing/m2.2b-tss-ist-evidence.md`.*
