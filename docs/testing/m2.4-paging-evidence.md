## Normal boot with the kernel's own page tables

```sh
zig build boot-test
```

Relevant serial output (CRLF removed):

```
[azura] page tables: the firmware's (CR3=0x1f401000), the kernel's own are M2.4
[azura] paging: EFER before=0xd00 after=0xd00
[azura] paging: building tables, old CR3=0x1f401000
[azura] paging: descriptors mapped
[azura] paging: W^X applied, switching CR3
[azura] paging: CR3 written
[azura] paging: released boot services quarantine, free frames 113063 -> 122983
[azura] paging: new page tables at 0x130000, CR3=0x130000
[azura] paging: text=0x100000..0x1068d4 rodata=0x107000..0x10981c data=0x10a000..0x10a000 bss=0x10a000..0x12f150
[azura] post-ExitBootServices: stack=ok gdt=ok idt=ok tss=ok ist=ok frames=ok framebuffer=ok memory_map=ok
[azura] boot complete, halting
```

What each value proves:

* `EFER before=0xd00 after=0xd00` — NXE (bit 11) was already set by the
  firmware and stays set. The kernel does not clear it.
* `old CR3=0x1f401000` — the inherited firmware value, logged before the
  switch as in every previous milestone.
* `descriptors mapped` — every non-`unusable` descriptor and the framebuffer
  MMIO were identity mapped before the switch.
* `released boot services quarantine, free frames 113063 -> 122983` — about
  9,920 frames (38.75 MiB) of boot services memory joined the allocatable
  pool after the switch, and the firmware's table frames were released first.
* `new page tables at 0x130000, CR3=0x130000` — the kernel chose the PML4
  address and the processor accepted it.
* `text=... rodata=... data=... bss=...` — the kernel sections were
  re-mapped with W^X permissions after the writable identity map.
* The post-transition summary is unchanged, so the stack, GDT, IDT, TSS,
  IST, frames, framebuffer and memory map all survived the switch.

## Controlled page fault

Image built with `-Dfault-mode=page_fault` and booted with OVMF:

```
[azura] paging: new page tables at 0x130000, CR3=0x130000
[azura] fault injection requested, reading an unmapped page
[azura] KERNEL FAULT: vector 14 (page fault)
[azura] KERNEL FAULT: rip=0x103741 cs=0x8 rflags=0x10006
[azura] KERNEL FAULT: error_code=0x0
[azura] KERNEL FAULT: cr2=0xdead0000
[azura] KERNEL FAULT: handler stack=0x1e00bca7
[azura] KERNEL FAULT: machine halted
```

The handler reports the faulting address in `CR2`, and the handler stack
lies in the boot stack, so the page fault did not use the IST.

## Regression

`zig build test` passed with the new tables active:

* boot test: PASS
* fault test: PASS (`#UD` and `#GP`, handler stack in the boot stack)
* ExitBootServices retry: PASS (key 0x731 rejected, 0x733 accepted)
* double fault: PASS (IST 0x129190..0x12d190, handler 0x12d127)

## Limitations of this evidence

* Everything was measured in QEMU/OVMF; no physical hardware was exercised.
* The kernel uses 4 KiB leaves only; large pages are not implemented.
* There is no user mode, no per-process address spaces and no TLB
  shootdown. The kernel runs with interrupts disabled on one CPU.
* The controlled page fault is an injected fault, not a spontaneous one.
* The `data` section is empty in this build (all globals are in `.bss`);
  the W^X mapping still covers it.
