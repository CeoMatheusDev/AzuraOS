# M2.2 — `ExitBootServices`: criteria of acceptance

This document records the acceptance criteria for M2.2, agreed before the
implementation starts, so that "done" has a definition that does not depend
on who is asked.

Status: **implemented** on `feat/m2-exit-boot-services`; merge into `main`
pending. Measured evidence: `docs/testing/m2.2-exitbootservices-evidence.md`.

## Context

Until now the kernel runs inside the environment the firmware left behind:
the firmware's page tables, the firmware's GDT (until M2.1), and the UEFI
boot services still available. Calling `ExitBootServices` tells the firmware
to release the resources it owns and to stop touching the machine, and it
returns the memory map with a **new key**. From that point on the kernel is
on its own.

The transition is not a single instruction. It has a defined order, and every
step has a precondition.

## Two distinct operations

`ExitBootServices` and the installation of the kernel's own page tables are
**different operations**, and the order matters:

* `ExitBootServices` may be called first, while the firmware's page tables
  are still active. The kernel then owns the machine but still uses the
  firmware's mapping.
* The kernel's own page tables may be installed first, while the boot
  services are still available. The kernel then owns the mapping but must
  still be able to call the firmware, which requires the firmware's
  services to be reachable.

The implementation may be split into steps, but the sequence must guarantee
that **no address the kernel still needs becomes unmapped**. That is the
single hardest requirement of this milestone.

## Where the call happens

The bootloader performs the call, not the kernel: it owns the image handle
and the system table, and the kernel never receives either of them. The
kernel's role is to prove that the transition happened and that the
environment survived it:

* the bootloader calls `ExitBootServices` with the key of its final memory
  map snapshot, retries with a fresh key on `EFI_INVALID_PARAMETER`, and
  jumps only after a success;
* the kernel refuses to start unless `boot_services_exited == 1`, and checks
  the stack, the GDT, the IDT, the framebuffer and the memory map before it
  does anything else.

This split keeps the system table out of the kernel's address space
entirely: there is no boot services pointer for the kernel to drop, because
it never had one.

## Criteria of acceptance

1. **The UEFI memory map is obtained with an adequate size and capacity.**
   The buffer is sized for the map the firmware reports, and no code assumes
   a fixed entry count.
2. **`EFI_BUFFER_TOO_SMALL` is handled.** The firmware may report that the
   buffer was too small and how much it needs; the bootloader retries with
   an adequate buffer instead of failing.
3. **The current memory map key is used.** The key returned by the last
   `GetMemoryMap` is the one passed to `ExitBootServices`. A stale key makes
   the call fail with `EFI_INVALID_PARAMETER`.
4. **A controlled retry is implemented** for the case where
   `ExitBootServices` returns `EFI_INVALID_PARAMETER`: the memory map is
   fetched again, the key is refreshed, and the call is retried. The
   specification allows the map to change between the two calls.
5. **No boot service is called after a successful transition.** The
   bootloader's boot services pointer is dropped, and the code that could
   still reach it is removed or made unreachable. The kernel never receives
   the system table, and its own memory management takes over.
6. **Every mapping the kernel needs survives the transition.** Concretely,
   the following must remain accessible and valid afterwards:
   * the kernel's code and data,
   * the kernel stack,
   * the GDT and the IDT,
   * the framebuffer, if the kernel is going to keep using it,
   * the boot structures allocated from the firmware's pool, including the
     memory map itself and the initial kernel stack.
7. **The startup and the exception paths are covered by automated tests**,
   and the M1 boot and fault tests do not regress.

## What is explicitly out of scope for M2.2

* The kernel's own page tables. Those are M2.4. M2.2 may leave the
  firmware's mapping in place, and it must say so in the log.
* The physical memory manager (M2.3) and the heap (M2.5).
* The TSS and the IST stacks. The user raised this explicitly: before
  interrupts become complex or processes are isolated, the kernel needs a
  TSS with an alternate stack for critical faults, in particular `#DF`.
  That is a separate step, scheduled right after M2.2, because without a TSS
  a fault on the kernel stack cannot be reported.

## Expected evidence

The milestone is only closed when:

* the serial log shows the memory map key before and after the transition,
  and the outcome of the call;
* the log shows that the kernel stack, the GDT, the IDT and the framebuffer
  are still reachable afterwards, for example by writing and reading back a
  known value at each of those addresses;
* the fault injection test still reports the exception, which proves the IDT
  and the stack survived;
* the boot test and the fault test pass without regression.

## Measured evidence

The measured results are in
`docs/testing/m2.2-exitbootservices-evidence.md`:

* normal boot: `ExitBootServices` succeeds on the first attempt, the kernel
  receives the same key and reports the post-transition checks as `ok`;
* stale key: the test build allocates between the snapshot and the call,
  OVMF rejects the key, the bootloader refreshes it (0x731 -> 0x733) and
  succeeds on the second attempt;
* fault injection: both the error-code and the no-error-code frames are
  reported after the transition, with `cs=0x8`;
* `zig build test` passes, including the M1 boot and fault tests.
