# M2.4 — Own paging: criteria of acceptance

This document records the acceptance criteria for M2.4, the milestone that
gives the kernel its own page tables. It was written with the implementation
so that "done" does not depend on who is asked.

Status: **implemented and merged into `main` in `58dfadc` (PR #7).**
Evidence: `docs/testing/m2.4-paging-evidence.md`. The decision is recorded
in `docs/adr/ADR-0010-own-paging.md`.

## Context

M2.3 left the kernel with a frame allocator but still running on the
firmware's page tables. The kernel could allocate physical memory but could
not control execution, write or read permissions, and the boot services
quarantine could not be released.

M2.4 builds and installs the kernel's own 4-level page tables, switches
`CR3`, releases the firmware tables and the boot services quarantine, and
proves that an unmapped access is reported with its address.

## Design summary

* 4-level x86_64 paging with 4 KiB leaves. `EFER.NXE` is enabled before any
  table is built.
* The NX bit is only set on leaf entries. Intermediate (table) entries keep
  it clear, because it is a reserved bit there.
* Identity map of every non-`unusable` descriptor, plus the framebuffer MMIO.
* W^X for the kernel image: `.text` read/execute, `.rodata` read/no-execute,
  `.data` and `.bss` read/write/no-execute. The kernel sections are aligned
  to 4 KiB in the linker script.
* Table frames come from the frame allocator and are zeroed.
* The switch happens with interrupts disabled; the old tables and the boot
  services quarantine are released afterwards.
* The page fault handler reports `CR2`.

## Criteria of acceptance

1. **The kernel builds its own tables.** The boot log shows the new PML4
   address, the `CR3` read back equals it, and the inherited `CR3` is
   logged before the switch.
2. **The switch is transparent.** The boot completes after the switch: the
   stack, GDT, IDT, TSS, IST, framebuffer checksum, memory map and frame
   allocator all keep working, and the post-transition summary is unchanged.
3. **W^X holds.** `.text` is executable and not writable, `.rodata` is
   readable and not executable, `.data` and `.bss` are writable and not
   executable. The boot log prints the four ranges.
4. **The boot services are released.** The free frame count rises by the
   boot services frames after the switch, and the log reports the delta.
5. **The firmware tables are released.** Their frames are returned to the pool
   without corrupting the new tree.
6. **A controlled page fault is reported.** With `-Dfault-mode=page_fault` the
   handler reports vector 14, `cs=0x8`, and `cr2=0xdead0000`. The handler
   stack stays in the boot stack.
7. **No regression.** The boot test, the fault handler test, the stale key
   retry and the double fault test all pass with the new tables. `zig fmt`
   and `zig build` pass.

## What is explicitly out of scope for M2.4

* User mode, per-process address spaces and ring 3.
* Large pages (2 MiB / 1 GiB leaves).
* TLB shootdown and SMP.
* Demand paging and page reclamation beyond the boot services release.
* Physical hardware validation. The evidence is QEMU/OVMF only.

## Expected evidence

* Boot log: `EFER` with NXE set, inherited and new `CR3`, table address,
  section ranges, the boot services release delta, and the unchanged
  post-transition summary.
* Page fault log: vector 14, `cr2=0xdead0000`, handler stack in the boot
  stack.
* `zig build test` passing every step.

## Measured evidence

See `docs/testing/m2.4-paging-evidence.md`. On the 512 MiB QEMU/OVMF machine
the allocator reported 113,063 free frames before the release and 122,983
after it, and the boot completed with the post-transition summary unchanged.
