# M2.3 — Physical frame allocator: criteria of acceptance

This document records the acceptance criteria for M2.3, the first milestone
that hands out physical memory. It was written with the implementation so
that "done" does not depend on who is asked.

Status: **implemented and merged into `main` in `870b677` (PR #6), with CI
green on `main` (run 39635441041).** Evidence:
`docs/testing/m2.3-frames-evidence.md`. The decision is recorded in
`docs/adr/ADR-0009-physical-frame-allocator.md`.

## Context

M2.2 left the kernel with a validated pre-`ExitBootServices` memory map, the
firmware gone for boot services purposes, and the ownership policy in
ADR-0007. The kernel still runs on the firmware's page tables; M2.4 will
replace them.

M2.3 adds a physical frame allocator that can answer two questions without
guessing:

* may this 4 KiB frame be handed out?
* can a frame that was handed out be returned?

The allocator must not touch the kernel image, the boot stack, `boot_info`,
the memory map buffer, the framebuffer, the runtime services regions, ACPI
tables, MMIO or the boot services memory that still holds the active page
tables. It must also fail closed when the map is malformed or the bookkeeping
is too small.

## Design summary

* 4 KiB frames, one bit per frame: 1 = used/reserved, 0 = free.
* Static 128 KiB bitmap in `.bss`, covering 4 GiB (1,048,576 frames); the
  used prefix is sized from the map.
* All bits start used. Only `conventional` descriptors are freed.
* Boot services are covered by the bitmap but stay used and are counted as
  quarantined; M2.4 releases them after installing the kernel's own page
  tables.
* Explicit reservations: first 1 MiB, kernel image, boot stack, `boot_info`,
  map buffer, framebuffer.
* First-fit allocation with a rotating hint; release resets the hint to the
  lowest released frame.
* Release rejects unaligned addresses, out-of-range addresses and double
  frees.
* Boot self-test allocates three frames, writes both ends of each, releases
  them and requires the lowest one back.
* Host stress test exhausts a synthetic 64 MiB pool, releases every third
  allocated frame, reallocates them and checks that no reserved frame is ever
  returned.

The design and the rejected alternatives are in ADR-0009.

## Criteria of acceptance

1. **The bitmap starts closed.** A freshly initialised allocator has zero
   free frames, every covered frame reads as used, and allocation returns
   null. The host tests assert this for a full and for an exact-size bitmap.
2. **Free and reserve align correctly.** Freeing a range frees only the
   frames it completely covers; reserving a range marks every frame it
   touches, including partial frames at both ends. Ranges are clipped to the
   covered capacity and cannot wrap the address space.
3. **Allocation and release are sound.** Allocations are page aligned, inside
   the pool, unique until released, and the free count changes by exactly
   one per operation. Releasing the lowest frame and allocating again returns
   that frame. Unaligned, out-of-range and double releases return the
   documented errors.
4. **The pool can be exhausted and recovered.** The host stress test
   allocates every free frame of a 64 MiB map with a kernel-like reservation,
   verifies that none is in a reserved range and that no address repeats,
   releases a deterministic subset, reallocates exactly that many frames with
   a second duplicate check, and restores the original free count.
5. **Only conventional memory is free.** The kernel frees `conventional`
   descriptors only. Boot services, loader code/data, runtime services, ACPI,
   reserved, unusable, PAL, persistent memory, MMIO and unknown types remain
   used. The boot log reports the boot services total as quarantined.
6. **The kernel's own memory is reserved.** The first 1 MiB, the kernel
   image (including the TSS, IST stack and bitmap), the boot stack,
   `boot_info`, the map buffer and the framebuffer are not allocatable. The
   boot self-test independently checks each allocated frame against those
   ranges before writing to it.
7. **The allocator fails closed.** A map with no conventional memory, a
   descriptor that wraps the address space, a bitmap that is too small, an
   invalid allocation or a failed write/read stops the boot with `FATAL`
   instead of continuing with a partially valid pool.
8. **The boot self-test is real.** The kernel allocates three frames, writes
   a pattern at the first and last 8 bytes of each, reads it back, releases
   them, and reallocates the lowest. The post-transition summary includes
   `frames=ok`, and the boot test requires the allocator and self-test
   markers in order.
9. **Regression.** The boot test, the `#UD`/`#GP` fault test, the
   `ExitBootServices` retry test and the forced double fault test all pass
   with the allocator active. `zig fmt --check` and `zig build` pass.

## What is explicitly out of scope for M2.3

* The kernel's own page tables, W^X, NX and controlled page faults (M2.4).
* Releasing the boot services quarantine. This is deferred to M2.4 because
  the active firmware page tables live there.
* The kernel heap and allocation/fragmentation tests (M2.5).
* Large pages, NUMA, memory hotplug, per-CPU pools and concurrency. The
  kernel runs with interrupts disabled and one CPU context.
* Per-frame reference counts and ownership tokens. There is one owner and
  the only release path is the boot self-test.
* Physical hardware validation. The evidence is QEMU/OVMF only.
* Memory above 4 GiB. It is reported and ignored; the static bitmap does not
  cover it.

## Expected evidence

* Host tests: `zig test kernel/mm/frames.zig` passes all eight tests,
  including the exhaust/release/reuse stress test.
* Normal boot: `frame allocator:` lines with total, free and used counts,
  the bitmap size, the quarantined boot services, the ignored memory above
  4 GiB, the explicit reservation line, the self-test addresses, and the
  post-transition summary ending in `frames=ok`.
* Fault test and double-fault test: the allocator and its self-test run
  before the injected fault and the summary includes `frames=ok`.
* `zig build test` passes every step.
* CI green on the pull request and, after the merge, on `main`.

## Measured evidence

See `docs/testing/m2.3-frames-evidence.md`. On the 512 MiB QEMU/OVMF
machine the allocator reported:

```
frame allocator: 130904 frames, 118579 free, 12325 used (511 MiB covered)
frame allocator: bitmap=16363 bytes, boot_services=42 MiB quarantined, above 4 GiB=0 MiB ignored
frame allocator: reserved low 1 MiB, kernel image, boot stack, boot_info, map and framebuffer
frame allocator: self-test ok, allocated 0x12e000 0x12f000 0x130000 and reused 0x12e000
```

The first free frame is above `kernel_end=0x12d200`; the self-test does not
touch the kernel image or the IST stack.
