# M2.2b — TSS and IST: criteria of acceptance

This document records the acceptance criteria for M2.2b, the step that gives
the kernel an alternate stack for critical faults. It was written with the
implementation so that "done" does not depend on who is asked.

Status: **implemented** on `feat/m2.2b-tss-ist` (PR #5, green CI). Measured
evidence: `docs/testing/m2.2b-tss-ist-evidence.md`; the decision is recorded
in `docs/adr/ADR-0008-tss-and-ist.md`.

## Context

M2.1 installed the kernel's own GDT and M2.2 removed the firmware from the
machine. Every exception still runs on the stack of the interrupted context.
For an ordinary fault on a healthy stack that is correct; for `#DF`, `#NMI`
and `#MC` it is not, because those faults may be caused by the stack itself.

A `#DF` raised while delivering another fault on a broken stack has no valid
stack to report on. Without an IST the processor gives up with a triple
fault: the machine resets and the serial log ends with no explanation. The
TSS is the architectural mechanism that provides an alternate stack.

## Design

### TSS

A 64-bit TSS, 104 bytes, in `.bss`:

| Offset | Field | Value |
| ------ | ----- | ----- |
| 0 | reserved | 0 |
| 4 | `rsp0` | boot stack top (no ring 3 yet) |
| 12, 20 | `rsp1`, `rsp2` | 0 |
| 28 | reserved | 0 |
| 36 | `ist1` | top of the 16 KiB alternate stack |
| 44..92 | `ist2..ist7` | 0 |
| 92, 100 | reserved | 0 |
| 102 | `iomap_base` | 104 (no I/O permission bitmap) |

The structure is packed: `rsp0` is at byte offset 4, not 8. Zig rounds
`@sizeOf` up to the struct alignment (112), so the GDT limit and the I/O map
base use the architectural size constant (104), not `@sizeOf`.

### GDT descriptor

The TSS descriptor is a 16 byte system descriptor at selector `0x18`
(indices 3 and 4), limit 103, byte granularity, access `0x89` (present, DPL 0,
type 9 — available 64-bit TSS). `LTR` changes the type to 11 (busy); the boot
check expects the busy value.

If the firmware code selector used during the transition names index 3 or 4,
the kernel refuses to boot instead of overwriting half of the descriptor.

### IST policy

| Vector | Exception | IST |
| ------ | --------- | --- |
| 2 | NMI | 1 |
| 8 | double fault | 1 |
| 18 | machine check | 1 |
| all others | — | 0 (interrupted stack) |

The policy is in `kernel/arch/x86_64/ist.zig`, which has no inline assembly
and is covered by the host unit tests.

### Order

1. provisional IDT, firmware code selector, IST 0;
2. fill the TSS, probe the IST stack;
3. load the GDT with the TSS descriptor;
4. `LTR 0x18`, verify the task register and the descriptor;
5. final IDT, kernel code selector, IST per the policy;
6. verify the stub addresses and the IST fields;
7. continue the boot.

The provisional IDT must not name IST1: the kernel TSS is not loaded yet, and
the processor would read the IST from the firmware's TSS.

## Criteria of acceptance

1. **The TSS has the architectural layout.** `rsp0` is at byte 4, `ist1` at
   byte 36, the total size is 104 bytes, and the offsets are compile-time
   checked and unit-tested.
2. **The descriptor is valid and unique.** It is encoded at selector `0x18`,
   it round-trips through the decoder to the kernel's TSS base and limit 103,
   and the boot fails if the transition alias would collide with it.
3. **The processor loads the TSS.** `LTR 0x18` succeeds, the task register
   reads back `0x18`, and the descriptor is busy afterwards.
4. **The alternate stack exists and is usable.** `ist1` is the top of a
   16 KiB stack in `.bss`, the stack is writable at its top before any fault,
   and the boot refuses to continue otherwise.
5. **Only the critical vectors use IST1.** The IDT gates for vectors 2, 8 and
   18 name IST 1; every other exception gate names 0. The kernel verifies all
   32 gates at boot.
6. **A real double fault is reported on the alternate stack.** With the
   `double_fault` injection, the processor raises `#DF` through vector 8, the
   handler reports vector 8, error code 0 and `cs=0x8`, and its stack pointer
   is inside the IST range and outside the interrupted stack. A wrong TSS
   would triple fault, so the test also asserts a single boot.
7. **Ordinary faults do not use the IST.** The existing `#UD` and `#GP` tests
   still pass and their handler stack is inside the boot stack.
8. **No regression.** The boot test and the `ExitBootServices` retry test
   pass, and `zig build test` passes.

## What is explicitly out of scope for M2.2b

* Recovering from a critical fault. The handler reports and halts; a future
  milestone may return or panic differently.
* Per-task kernel stacks and ring 3. `rsp0` points at the boot stack until a
  scheduler exists.
* An I/O permission bitmap.
* Separate IST stacks per critical vector. The current handlers never return,
  so one stack is enough; see ADR-0008 for the limitation.
* The physical allocator (M2.3) and the kernel's own page tables (M2.4).

## Expected evidence

* Boot log: the TSS base, limit 103, `rsp0`, `ist1`, the IST stack range, the
  task register `0x18`, the descriptor with access `0x8b`, and the IDT IST
  verification.
* Double fault log: vector 8, error code 0, `cs=0x8`, handler stack inside the
  IST range, exactly one bootloader banner.
* Ordinary fault logs: handler stack inside the boot stack.
* Unit tests for the TSS layout, the descriptor round trip, the IST policy and
  the stack probe.
* `zig build test` with every QEMU test.

## Measured evidence

The measured results are in `docs/testing/m2.2b-tss-ist-evidence.md`:

* normal boot: `TSS loaded, task register=0x18`,
  `TSS descriptor: base=0x1066a0 limit=103 access=0x8b`,
  `IDT: IST 1 active for vectors 2, 8 and 18`, and the post-transition summary
  includes `tss=ok ist=ok`;
* double fault: vector 8, error code 0, `cs=0x8`, handler stack
  `0x10b767` inside the IST `0x1077d0..0x10b7d0`;
* ordinary faults: the handler stack stays inside the boot stack
  `0x1e00c018..0x1e010018`.
